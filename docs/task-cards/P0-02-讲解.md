## 0. 一句话：这一卡做了什么

把存储从"写死 SQLite"改成**同一套 DAO / 同一份 SQL 在两个 profile 下行为一致**：

- `sqlite`（默认，零依赖）：clone 下来不传任何参数就能跑；
- `postgres`（PostgreSQL 16）：`-Dspring-boot.run.profiles=postgres` 即可切过去。

改的只有三件事：**配置分层**（共用项 / profile 专属项）、**schema 按 dialect 拆成两个文件**、**SQL 去掉 SQLite 专有语法**。业务代码一行没动。

为什么现在做：P0-01 只有 SQLite。等 P0-02 主体把 `flow`/`flow_step`/`audit_log` 建完再改，就要重做一批 DAO + 重跑一批证据；现在改只动 6 个文件、零返工。

## 3. 逐文件讲解（作用 / 为什么这么写 / 改了会怎样）

### 3.1 `java-service/pom.xml`（改：+14 −2）

**作用**：加 `org.postgresql:postgresql`，**不写版本**（交给 `spring-boot-starter-parent` 的 BOM 管），`scope=runtime`。

**为什么这么写**：

- 不写版本 = 版本由 Spring Boot 统一裁决。写了版本就会出现"Boot 升了、驱动没升"的隐性漂移，而且这种漂移只会在线上某个时刻才暴露。
- `scope=runtime` 表达的是事实：编译期代码从不 `import org.postgresql.*`，驱动是由 `DriverManager` 按 URL 反射加载的。写成默认的 compile scope 会给人一种"代码里有用到 PG 类"的错觉。

**改了会怎样**：把 PG 驱动从 `runtime` 改成 `provided` → 打出来的 jar 里没有驱动，PG profile 启动时报 `No suitable driver found for jdbc:postgresql://...`。写死版本号 → 将来 Boot 升级时驱动版本不动，容易踩到驱动/Boot 的兼容问题。

### 3.2 `src/main/resources/application.properties`（改：只留共用项）

**作用**：端口 8000、`spring.profiles.default=sqlite`、`spring.sql.init.mode=always`、`spring.sql.init.schema-locations=classpath:schema-${spring.sql.init.platform}.sql`、日志 pattern。

**为什么这么写**：

- `spring.profiles.default=sqlite`（而不是 `active`）：用户没显式指定就落到 sqlite，**显式指定则完全由用户说了算**。用 `active` 会把 sqlite 变成"删不掉"的默认值。
- `schema-locations` 显式写成 `classpath:schema-${spring.sql.init.platform}.sql`，而不是依赖 Boot 的 `schema-${platform}.sql` 默认约定：**文件名写错时要"启动即失败"**，而不是静默跳过初始化、让服务带着空库跑起来（后者的故障形态是"接口 500，但你以为是代码问题"）。
- `platform` 本身放在各自的 profile 文件里（见 3.3/3.4），而不是写 `platform=${spring.profiles.active:sqlite}`：后者在"多 profile 叠加"时会拿到 `postgres,postgres-local` 这种字符串，直接拼出一个不存在的文件名。

**改了会怎样**：把 `spring.sql.init.mode` 改成 `embedded`（Boot 默认）→ SQLite 仍会初始化，但 PG 这种"非内嵌数据源"会被静默跳过初始化，PG profile 起得来但表不存在。

### 3.3 `src/main/resources/application-sqlite.properties`（新）

**作用**：SQLite URL（`jdbc:sqlite:${app.db.path:data/mock-oa.db}?busy_timeout=5000`）、驱动 `org.sqlite.JDBC`、Hikari `maximum-pool-size=1`、`spring.sql.init.platform=sqlite`。

**为什么这么写**：连接池=1 是刻意的：**SQLite 是单写者**，多连接并发写只会换来 `SQLITE_BUSY`。用"串行"换"确定性"，对 mock 服务是划算的交易。`busy_timeout=5000` 是第二道保险。

**改了会怎样**：把 pool 开到 10 → 并发写开始出现 `SQLITE_BUSY`，而且**偶发**（最难受的故障形态）。去掉 `busy_timeout` 同理。

### 3.4 `src/main/resources/application-postgres.properties`（新）

**作用**：`spring.config.import=optional:classpath:application-postgres-local.properties`；PG URL `${PG_URL:jdbc:postgresql://127.0.0.1:5432/p2p_agent}`、驱动、`${PG_USER:p2p_agent}`、密码 `${PG_PASSWORD}`、Hikari `maximum-pool-size=10`、`spring.sql.init.platform=postgres`。

**为什么这么写**：

- **密码只允许来自"环境变量"或"本地未提交文件"**：本文件里只有占位符 `${PG_PASSWORD}`，且不给默认值 → 两者都没有时启动即失败（`Could not resolve placeholder`），而不是带着空密码去撞数据库。**快速失败优于模糊失败**。
- `optional:` 前缀：本地文件不存在时不让启动失败（CI / 别人的机器上用环境变量即可）；这行是"让用户已有的本地文件真的生效"的唯一机制（Spring Boot 不会自动加载 `application-postgres-local.properties`，因为 profile 名是 `postgres` 而不是 `postgres-local`）。
- 连接池=10：PG 是真并发数据库，pool 才敢开大。**这也是本卡第 3 条验收能在 PG 上测出真并发的前提**（SQLite 那边 pool=1，并发请求实际被串行化了）。

**改了会怎样**：删掉 `spring.config.import` → 用户放进本地文件的密码被忽略，PG profile 直接认证失败；给 `${PG_PASSWORD}` 加上 `:` 空默认值 → 配置缺失时不再快速失败，变成运行时认证错误。

### 3.5 `schema.sql` → `schema-sqlite.sql` + `schema-postgres.sql`

**作用**：两份 DDL 都建 `idempotency(request_id TEXT PRIMARY KEY, response_json TEXT NOT NULL, trace_id TEXT, created_at TEXT NOT NULL)`，均由 `spring.sql.init.platform` 按文件名选中。

**为什么这么写**：两份现在**内容一致**，因为它们只用两库共通的子集（`TEXT` / `PRIMARY KEY` / `NOT NULL`，无自增、无方言类型）。分开写不是为了现在就分叉，而是为了：

1. 让"平台选择"这件事可验证（见 §4.A0/B0 的 `Executing SQL script from class path resource [schema-*.sql]`）；
2. 留出**必然会出现**的分叉位置：PG 侧的 append-only 审计（`REVOKE UPDATE, DELETE ON audit_log FROM p2p_agent;`）是 SQLite 做不到的，将来只能写在 PG 文件里（已在文件头注释标注计划）。
- 幂等：`CREATE TABLE IF NOT EXISTS`，重复启动不报错。

**改了会怎样**：把两份合并成一份带分支的脚本 → SQL 初始化不支持条件分支，只能在应用启动时插 Java 判断，把"schema 管理"塞进业务代码；删掉 `IF NOT EXISTS` → 第二次启动直接失败。

### 3.6 `service/ApprovalService.java`（改：两条 SQL 通用化）

**作用**：写路径从 `INSERT OR IGNORE`（SQLite 专有）改成 `INSERT INTO idempotency(...) VALUES (?,?,?,?) ON CONFLICT(request_id) DO NOTHING`（两库共通）；`SELECT` 不变（本来就是标准 SQL）。

**为什么这么写**：

- `ON CONFLICT` 在 PostgreSQL 9.5+ 与 SQLite 3.24+ 都支持，且**冲突目标显式写成 `request_id`**（SQLite 要求显式冲突目标；PG 允许省略，但显式写出来两库才对得上，也让"唯一键是哪个"在 SQL 里可读）。
- 为什么不用 `ON CONFLICT DO UPDATE ... RETURNING`：我们不仅要"唯一"，还要区分**这次到底是首次还是重复**（首次 `dedup=false`、日志也不同）。`RETURNING` 给不出"这行是谁先写的"，两段式（先插、0 行则回读）更直白。
- 为什么保留回读重试（20×50ms）：`sqlite` profile 下 pool=1 用不到；**`postgres` profile 下 pool=10，这条路径是真的会被走到的**——A 线程插入未提交、B 线程冲突忽略后立刻回读可能读不到那一行。正常情况下 `JdbcTemplate` 无外层事务时每条语句自动提交，所以极少触发；这段重试挡的是"将来把两步放进同一个 `@Transactional`"之后的快照时序问题。

**改了会怎样**：把 `ON CONFLICT(request_id)` 写成不带冲突目标的 `ON CONFLICT DO NOTHING` → **SQLite 直接报语法错误**（SQLite 要求冲突目标）；把 `DO NOTHING` 改成 `DO UPDATE` → 语义从"返回首次结果"变成"覆盖首次结果"，幂等的定义就被悄悄改了，而接口签名看不出任何变化。

## 5. 简报点名要讲清的四件事（面试会追问）

### 5.1 为什么两份 schema，而不是一份带 dialect 分支

1. **SQL 初始化脚本没有条件分支能力**。要在"一份脚本"里区分 dialect，就得在应用启动时用 Java 判断再拼 SQL——把 schema 管理塞进业务代码，是最贵的做法。
2. **两份文件 = 两个可独立演进的 artifact**。PG 侧马上要加 append-only 的 `REVOKE`（SQLite 根本没有权限模型），这类语句天然只能属于 PG 文件。
3. **代价被明确限定**：两份内容是"共通子集"，重复的是几十个字符的 DDL，不是逻辑。真正的风险从来不是重复，而是"改了 A 忘了改 B"——这个风险靠 §4.A0/B0 的启动日志（每次启动都告诉你用了哪份脚本）+ 两库跑同一套断言来兜。

### 5.2 通用 SQL 子集到哪为止；再复杂怎么办

**当前子集边界**（本卡实际用到的）：

- DDL：`CREATE TABLE IF NOT EXISTS` + `TEXT` / `PRIMARY KEY` / `NOT NULL`；不用自增（`serial`/`identity`）、不用 dialect 类型（`timestamptz`/`datetime`）、不用 `COMMENT ON`、不用权限语句。
- DML：标准的 `INSERT ... VALUES`、`SELECT ... WHERE`、`UPDATE`、`DELETE`；唯一用到的高级语法是 **UPSERT，且用两库共同实现的 `ON CONFLICT(<target>) DO NOTHING` 形式**。
- 明确**不用**：`INSERT OR IGNORE` / `INSERT OR REPLACE`（SQLite 专有）、`RETURNING`（两库行为与版本要求不一致）、窗口函数/JSON 函数/`ILIKE` 等方言差异大的地方。

**再复杂怎么办（P1 的预案）**：如果业务 SQL 开始分化（比如要做复杂报表、`RETURNING` 多行、PG 的 `jsonb` 检索），就不要继续维持"一份 SQL 两边跑"这个约束了——**改用 Flyway 按 dialect 管迁移**：`db/migration/{vendor}/V1__init.sql`，让每个库各自拥有自己的迁移历史，同时把"迁移版本一致性"交给工具而不是人。**本卡不引 Flyway 的理由**：现在只有 1 张表、2 条语句，引它属于为 5 行的复杂度付 500 行的运维成本。

### 5.3 两个 profile 的连接池为什么不一样（1 vs 10）

- **SQLite**：单写者模型，写操作会锁库文件。多连接并发写不会更快，只会换来 `SQLITE_BUSY`。pool=1 把"串行"变成显式事实，也让 P0-01 的幂等语义在单进程内绝对确定。
- **PostgreSQL**：MVCC，写并发由数据库自己协调（唯一键 + `ON CONFLICT` 保证幂等）。pool=10 才能让"5 并发同 request_id 只建 1 行"这类断言**测出真实并发**，而不是被连接池串行化后的假并发。
- 数字本身不是重点，**重点是"池大小跟着存储引擎的并发模型走"**，而不是抄一个默认值。

### 5.4 为什么 `created_at` 用 `TEXT` 存 ISO-8601，而不是 `timestamptz`

- **和 HTTP 契约一致**：接口里的 `created_at` 本来就是字符串（P0-01 约定），存成时间类型就要在两处做映射，映射就有时区歧义。
- **跨库跨语言零类型映射**：`Instant.toString()` 写进去、读出来就是同一个字符串，Java/Python/sqlite3/psql 四方看到的都一样，不依赖各家的时区设置。
- **代价要说清楚**：TEXT 排序恰好也是时间序（ISO-8601 的设计目的），但**范围查询与索引效率不如原生时间类型**。P2 若真要做时间范围查询，正确做法是**加一列 `created_at_ts timestamptz` 专门用于索引与查询**，而不是把契约里的 `created_at` 改成时间类型——契约是给调用方看的，别为了内部优化改契约。

- 回归套件脚本目前放在 **gitignored 的 `java-service/target/suite/`** 下（本卡范围只允许 6 个文件，所以没有入库）。它现在是这个项目唯一的端到端回归资产，建议 Hermes 决定是否收录到 `scripts/`（P0-02 主体每加一个端点都值得跑一遍）；
- 未验证：另起一个空库（全新 PG database）时 schema 初始化 + 全断言的完整回归（本卡是 `DROP TABLE` 后由启动重建，等价于空表场景，但不等于空库场景）。

## 8. 环境坑实录（本轮新增，给后续会话省时间）

1. **`mvn clean` 会清空 `java-service/target/`**：我把回归套件放在 `target/suite/` 下，第一次 `mvn clean` 之后它消失了（表现出来是 `pwsh -File` 报"无法识别为脚本文件名"）。教训：临时脚本别放在会被 clean 的目录里，或者先建目录再重定向输出（`cmd /c "... > target\x.log"` 在目录不存在时也会失败）。
2. **PowerShell 里 `(if (...) {...} else {...})` 不是表达式**：`Write-Output ("a" + (if ($x) {"b"}))` 会直接报"if 不是 cmdlet"。赋值形式 `$v = if (...) {...}` 才合法。我的断言函数第一版因此丢掉了全部明细行（只有计数是对的）——**这是"输出看起来正常、其实证据缺失"的典型陷阱**，改完重跑才拿到逐条证据。
3. **`pwsh -File` 要用绝对路径**：相对路径在本轮的工具调用里解析不到（工作目录与预期不一致）。
4. **psql 的 NOTICE 走 stderr**：`\dt` 在无表时把 "Did not find any relations" 写到 stderr，`Tee-Object` 只收 stdout，所以混合捕获时要注意顺序；本轮改成"脚本 + Tee"模式后顺序稳定。
5. **不要用 `2>&1 | Tee-Object` 捕获原生命令输出**（本轮 B2/C1 第一次就是这么丢的）：改成一个 `.ps1` 脚本内部依次调用原生命令，再对**脚本整体**输出做 `Tee-Object`，内容才完整落盘。

P0-02 §0 回归套件：21 项断言，对任意 profile / 端口跑同一份。
用法：pwsh -NoProfile -File <本文件> -BaseUrl http://127.0.0.1:8000 -Label sqlite
#>
param(
  [string]$BaseUrl = "http://127.0.0.1:8000",
  [string]$Label = "sqlite",
  [string]$Work = "$PSScriptRoot"
)
$script:pass = 0
$script:fail = 0

function Check([string]$name, [bool]$ok, [string]$detail) {
  if ($ok) { $script:pass++ } else { $script:fail++ }
  if ($ok) { $tag = "[PASS]" } else { $tag = "[FAIL]" }
  $line = $tag + " " + $name
  if ($detail) { $line = $line + "  | " + $detail }
  Write-Output $line
}

function Http([string]$method, [string]$path, [hashtable]$headers, [string]$body) {
  $hf = Join-Path $Work ("h_" + [guid]::NewGuid().ToString("N") + ".txt")
  $bf = Join-Path $Work ("b_" + [guid]::NewGuid().ToString("N") + ".txt")
  $cargs = @("-s", "--noproxy", "*", "-X", $method, "-D", $hf, "-o", $bf, "-w", "%{http_code}")
  if ($headers) { foreach ($k in $headers.Keys) { $cargs += @("-H", ($k + ": " + $headers[$k])) } }
  if ($body) { $cargs += @("-H", "Content-Type: application/json", "-d", $body) }
  $cargs += ($BaseUrl + $path)
  $code = & curl.exe @cargs
  $ht = if (Test-Path $hf) { Get-Content -Raw $hf } else { "" }
  $bt = if (Test-Path $bf) { Get-Content -Raw $bf } else { "" }
  Remove-Item $hf, $bf -Force -ErrorAction SilentlyContinue
  $h = @{}
  foreach ($line in ($ht -split "\r?\n")) {
    if ($line -match "^([A-Za-z][A-Za-z0-9\-]*):\s*(.*)$") { $h[$matches[1]] = $matches[2].Trim() }
  }
  $j = $null
  try { $j = $bt | ConvertFrom-Json } catch { }
  return [pscustomobject]@{ Status = [int]$code; Headers = $h; Body = ($bt.Trim()); Json = $j }
}

function IsUuid([string]$s) { return ($s -match "^[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}$") }

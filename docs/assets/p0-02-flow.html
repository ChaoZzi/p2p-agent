P0-02 主体：一次采购请求的完整链路
场景：员工跟数字员工说一句「帮我采购 100 个键盘，预算走 CC-1001」。
系统要把这句话变成一张受控的单据：建单 → 提交 → 请求审批 → 审批 → 完成，每一步都留下改不掉的记录。
下面 point 开每一步，能看到「谁在做」「碰到你写的哪个文件」「没有它会怎样」。
⚪ P0-01 已有 🔵 dsh 写的（接口层） 🟠 你写的 [你敲]
0员工说一句人话人 → 微信 / 演示页
人只说业务语言，不给结构化数据：「帮我采购 100 个键盘，走 CC-1001」。
这一步决定了整个项目的卖点：入口是自然语言，出口是收得住的企业流程。
↓ 这句话交给数字员工（Python 侧）
1Python 侧：把一句话变成结构化意图🔵 dsh 的 llm/deepseek.py ＋ 🟠 你以后写的 agents/intent.py
调 DeepSeek 做意图抽取，得到 {"item":"键盘","qty":100,"reason":"扩编","cost_center":"CC-1001"}； 再由 agent 决定调哪个工具（建单），并生成一次请求的身份：X-Request-Id（幂等键）与 X-Trace-Id（追踪号）。
这一层还没开工（P0-02 的最后一步）。它不做业务判断 —— 规则在 Java 侧的引擎里。
↓ HTTP 请求发出
2请求进入 Java：POST /api/flows⚪ TraceFilter ＋ 🔵 FlowController
  • TraceFilter（P0-01 已有）从 X-Trace-Id 取追踪号（没有就自己生成），放进 MDC，并回显响应头 —— 之后每一行日志都会带 [trace=…]。
  • FlowController（dsh 写）只做三件事：取请求头（X-Operator / X-Request-Id）、把 body 转成 CreateFlowCommand、调用 FlowService。它不做状态判断。
分层：Controller 管"协议"，Service 管"业务"，状态机管"规则"。
↓ 进入你写的调度员
3建单 + 连推两步状态 + 留痕🟠 FlowService（你写）
  • 3a 幂等：findByRequestId —— 同一个请求重复到达，直接返回原单（不重复建单）。
  • 3b 建单：insertFlow(状态 = DRAFT) → 审计 FLOW_CREATED。
  • 3c：transit(DRAFT→SUBMITTED) → 条件更新 → 审计 SUBMITTED。
  • 3d：transit(SUBMITTED→PENDING_APPROVAL) → 条件更新 → 审计 APPROVAL_REQUESTED。
为什么建单要连推三步：让"建单"这件事在审计里也留下完整的来龙去脉，而不是凭空冒出一张"待审批"的单。
没有 FlowService：这些零件谁会去调？没人编排 —— 系统不转。
↓ 每一步状态变更，都要问规则书 + 记账
4规则书：这次迁移合法吗？🟠 FlowStateMachine（你写）
每次改状态前问一句 transit(现在, 想去的)：合法就返回目标状态；不合法就抛 409 FLOW_STATE_CONFLICT，消息里写清 from -> to (allowed: […])。
没有它会发生什么（最危险的一个）：一张"已完成"的单可以被重新提交、被重复审批；驳回的单可以偷偷变成已批准。业务规则不能只写在心里。
5黑匣子：把这一步记下来🟠 AuditService（你写的） ＋ 🔵 AuditRepository
写一行 audit_log：谁(actor) 什么时候(at) 对 哪张单(flow_id) 做了 什么(action)、为什么(detail)，外加这次请求的 追踪号(trace_id)。
只增不改：代码层——仓储里根本没有 update/delete 方法；数据库层——PostgreSQL 上被 REVOKE 拒绝（实测过）；业务层——和状态变更同事务。
没有它：单子状态变了，但没人知道是谁改的 → 不可审计、无法追责。
6会话结束：返回给员工一个"待审批的单"Java → Python → 人
响应 FlowView（状态 PENDING_APPROVAL）→ Python 侧回一句人话：「已为你建单，等待张三审批」。
建单结束时：库里 1 行 flow + 审计 3 行。
↓ 审批人出手（人工节点 —— HITL）
7张三点"同意"：POST /api/flows/{id}/approve🟠 FlowService.approve
  • 先读出单子，用 FlowState.of(库里的字符串) 把状态翻译成枚举 🟠 FlowState（你写的）
  • transit(PENDING_APPROVAL→APPROVED) → 条件更新（把"我以为的旧状态"写进 WHERE）→ 审计 APPROVED，actor = 张三
  • transit(APPROVED→COMPLETED) → 条件更新 → 审计 COMPLETED
并发就发生在这里：张三和李四同时点"同意"，两个请求都读到 PENDING_APPROVAL， 但条件更新只让一个人拿到影响行数 1，另一个拿到 0 → 409。这就是"乐观锁"，也是面试必问的那道题。
审批完：审计共 5 行（创建/提交/请求审批/批准/完成），5 行 trace_id 相同。
8回放：GET /api/flows/{id}/audit演示页 / 面试现场
把这张单的流水按时间升序打出来 —— 谁、什么时候、做了什么、为什么，一目了然。
这是整个项目最值钱的一屏：一次自然语言请求，最终变成一条可追、可解释、改不掉的证据链。
9排障：拿一个 trace_id 串起两端⚪ TraceFilter ＋ 🔵 tracer ＋ 🟠 AuditService
同一个 trace_id 同时出现在：Python 侧 trace/<id>.jsonl、Java 日志 [trace=…]、以及审计表的 trace_id 列。
跨语言排障不用靠猜时间戳：一个号，三处对账。

# 协作规范 — P2P Agent 开发流程（v1.3）

> 角色：**Hermes（我）**= 需求/架构/审核；**dsh（DeepSeek harness）**= 编码执行；**你** = 核心代码手写 + 验收 + commit 把关。

## 1. 分工原则
- 需求与任务卡：Hermes 写，你确认后生效。
- 代码分三档，每张卡逐一标注：
  - `[你敲]`：核心理解件，你亲自写（面试追问深水区：agent loop / 状态机 / HITL / 幂等 等）。Hermes 提供行为规格，规格细到你能直接照着敲。
  - `[dsh写+讲]`：脚手架 / 配置文件 / 依赖 / 样板 / 基础设施。dsh 交付时必须附**《代码讲解》**：每个文件 1–3 句作用 + 关键设计决策。
  - `[dsh写]`：纯支持件（DTO / 测试数据 / 工具脚本），review 即可。
- 审核闭环：dsh 交付 → **Hermes 先审**（正确性 + 讲解与代码一致）→ 你验收 → 合入 → 下一张卡。

### 1.1 测试分工（v1.1，2026-09-27 起生效）
- **你只写实现**（`[你敲]` 文件），**不再手写测试**。
- **Hermes 负责为每个交付功能编写"独立验证测试"**，作为该功能的验收依据：
  - Java：`java-service/src/test/java/com/p2pagent/verify/<功能>VerifyTest.java`（独立包 `verify`，与实现者自己的测试分开）
  - Python：`python-service/tests/test_<功能>_verify.py`（pytest，已在 `pyproject.toml` dev 依赖里）
  - **由 Hermes 提交**（message 前缀 `test(verify):`）—— 让 git 历史一眼分出"实现 by 你 / 验证 by Hermes"
- **独立性铁律**：Hermes 写测试时**只依据规格 / 验收标准**（期望值从规格表手抄），**不读实现去反推行为** —— 否则测试只是复述实现，实现错了测试也跟着错。
- **闭环**：你交实现 → Hermes 写并跑验证测试 → **红了就是发现了 bug**（附失败断言 + 真实输出）→ 你修实现 → 再跑 → 绿 → 你验收 → 提交。
- **你能看见测试**：Hermes 每次给出 ①文件绝对路径 ②关键断言说明 ③实跑输出 ④你一键复跑的命令（绝对路径 / `.cmd`）。
- 你已经写过的 `FlowStateTest` / `FlowStateMachineTest` / `db/FlowRepositoryTest` **保留不动**（你的学习资产）；"穷举 / 边界 / 并发 / 契约形状"这类验收级覆盖由 Hermes 的 `verify` 测试承担。

## 2. 讲解要求（dsh 交付物标准）
> **v1.1 新增（用户痛点，2026-10-03）**：任何规格 / 任务卡 / 讲解，**必须先写"业务视角"再写实现细节** ——
> ① 它在业务里是谁（用一句人话打比方，如"留痕员 / 调度员 / 规则书"）
> ② 它在一个请求的哪一步被用到 ③ 它坏了业务上会怎样 ④ 一次真实请求走下来，各零件被碰到的顺序。
> **原因**：用户反馈"文档能看懂签名，但不知道这段代码在整个业务里干什么"。先给业务定位，再给接口。
> **范例**：`P0-02-你敲规格-Java.md` §0.5 的那张表和调用链。
>
> **v1.1 又一条（用户要求，2026-10-03）**：**给用户任何代码片段 / 实体（record、DTO、方法骨架）时，必须逐字段、逐行中文标注** ——
> 每个字段写清 ① 它是什么 ② **值从哪来 / 谁负责填** ③ 为什么需要它 ④ 不填或填错会怎样。
> 原因：用户是对着规格**亲手敲**这些代码的人，没有标注他就不知道该往参数里填什么（原话："你给我实体的时候麻烦标注上每个字段什么意思"）。
> 枚举同理：每个取值都要写清"业务含义 + 什么时候会被用到"。
>
> **v1.1 第三条（用户要求，2026-10-03 —— 形态上最重要的一条）**：**面向用户手写的需求 / 规格，必须给"编号的逐步业务流程"，不许只给要点让他猜** ——
> 每个方法拆成 `步骤 1 / 2 / 3 …`，每步写清：**做什么 → 调哪个方法（真名真签名）→ 值从哪来（入参 / 自己生成 / 常量）→ 失败怎么办（抛什么异常、什么状态码）**；
> 结尾给出"**跑完的结果**"（最终状态 + 审计行数）供自检。
> 范例：`P0-02-你敲规格-Java.md` §3.1（FlowService 四个方法的逐步流程）。
> 原因：用户原话 —— "**后面的关于我写的，需求要提明白，不要让我猜。你告诉我具体明确的业务流程就行，我直接照着这个流程敲代码，关键就是能让需求变得简单易懂。**"
>
> **v1.2（2026-10-03，用户第二次提醒）**：以上还不够 —— 规格还必须包含**"文件级改造清单"**，即：**动手前要先做哪几件事**（哪些文件是新建 / 哪些要把接口改成类 / 哪些要删除 / 依赖怎么注入），
> 以及**中间态会看到什么报错、为什么那是正常的**。
> 反面教材（真实发生）：`FlowService` 的需求没写"要把 interface 改成 class + 删掉 `FlowServiceStub`"，
> 用户只能靠追问才知道 —— 用户的评价原话："**你这个你都不写清楚，还得我问你才能指导**"。
> **固定格式（以后每条需求都用这个模板）**：
> ① 业务定位（它是谁 / 在哪一步被用到 / 坏了会怎样）→ ② 文件级改造清单（新建/改造/删除 + 注入）
> → ③ 编号逐步流程（每步：做什么 / 调谁 / 值从哪来 / 失败怎么办）→ ④ 预期报错 → ⑤ 完成自检清单（可勾选）。
>
> **v1.3（2026-10-16，用户第一次明确提出的"核心代码交付格式"—— 最高优先级）**：
> 凡是**要用户亲手敲**的代码（`[你敲]` 档），一律按**固定五段**给，缺一段都不算交付：
> ① **这段代码是干嘛的**（一段话，业务语言：它解决什么问题）
> ② **它处在整个请求的哪一部分**（在调用链的第几步；上游谁调它、它下游调谁）
> ③ **它与上下文的联系**（入参从哪来、返回值给谁用、与谁共享同一份状态/事务/ID）
> ④ **所有字段 / 变量逐条说明**（每个字段四件事：**是什么 / 值从哪来 / 为什么需要 / 不填或填错会怎样**；入参、返回值、常量、局部变量同样要标）
> ⑤ **把要写的代码贴出来**（完整可照抄的参考实现）
>
> **原因**：用户原话 —— "**我都里写的 有难度的有含金量核心的代码 首先是一段说明 这段代码是干嘛的 它处在整个请求的那个部分 和上下有什么联系 然后所有的字段要有说明是什么意思 然后就是把我要写的代码贴出来 防止我不会后 直接看代码 往下写。**"
>
> **与前几版的关系**：v1.1（业务视角 + 逐字段标注 + 编号流程）与 v1.2（文件级改造清单 + 预期报错 + 自检清单）**继续有效**，全部并进这五段里；**v1.3 新增的是"必须贴出完整参考实现"—— 早先"只给形状、不替他写"的约定作废。**
> **git 归属不变**：代码仍由用户亲手敲、自己 commit（`[你敲]` 的 git 历史仍是"他写过"的证据）；贴参考实现是为了**不让他卡住**，不是为了替他提交。
>
> **v1.4（2026-10-19，用户新要求 —— 五段之外的第 ⑥ 段：真实数据样本）**：
> 用户原话 —— "**写代码时新增一个要求 就是在实际调用时 参数的实际数据是长什么样的 得描述出来**"。
> 即：**每个参数 / 返回值，除了写类型与"值从哪来"，还必须贴出"实际调用那一刻"的真实数据**（真实 JSON / 真实字符串 / 真实 dict），
> 让人能拿它对照自己变量里到底该有什么。要求：
> ① **样本必须来自实跑**（替身 LLM 或真调用都行，但要在文档里注明来源），不许自己"想一个看着像的"；
> ② 区分三类来源：**模型真实输出**（不可信、可能缺键/类型错）、**我们构造的**（state / trace_id）、**后端真实响应**（Java 返回体）；
> ③ 长字段要标"已截断"，但结构（键名/嵌套）必须完整可见；
> ④ 样本要成对给出**入口与出口**：入参长什么样 → 返回值长什么样 → 落库/落 trace 那一行长什么样。
> **为什么**：类型注解只能表达"允许什么"，表达不了"实际是什么"。本次正是靠跑出真实样本，才发现在 `status=ok` 却明明是反问的 bug（模型把问句写成了句号结尾）。
> **范例**：`docs/task-cards/P0-02-你敲规格-Python.md` §3 的「⑥ 真实调用数据样本」。

每张卡交付包含：
1. 代码（只含本卡负责文件）
2. `讲解.md`：逐文件说明"这段代码的作用是什么、为什么这么写、改了会怎样"
3. 自测结果：能跑的证据（命令输出/截图）

Hermes 审核时检查：讲解是否与代码一致、是否覆盖关键决策、有无含糊带过。

## 3. Commit 纪律
- 一个功能 = 一个 commit；message 用 `feat:` / `fix:` / `docs:` 前缀。
- **你敲的文件由你 commit；dsh 只 commit 自己负责的文件**（dsh 提交时排除 `[你敲]` 文件）。
- **`verify` 测试由 Hermes commit**（前缀 `test(verify):`），与你的实现提交分开 —— 历史一眼看出"谁写的实现、谁做的独立验证"。
- git 历史 = 面试证据：你的 commit 是你亲手写的部分。

## 4. 阶段推进（最小系统优先）

# 评审报告：P2P Agent 是否适合作为「Agent 应用开发工程师」面试项目

> 评审对象：docs/PRD.md（v0.1，姜盛超 × Hermes）
> 候选人画像：本科应届，目标岗位「Agent 应用开发工程师」，语言诉求 **Java + Python 结合**
> 评审方法：抓取并对照 2026 年真实招聘 JD（校招 + 社招 + 平台岗）+ BOSS直聘岗位要求汇总 + Agent 面试题库
> 说明：本报告基于当前可公开获取的招聘信息样本（时间窗口约 2025-12 ~ 2026-09），链接均可点击核对。

---

## 0. 结论速览

**判断：适合，且是当前校招市场上"卡位很好"的一类项目——但 PRD 现在有 3 个必改点，改完才真正匹配"你这个人 + 你要投的岗位"。**

| 维度 | 评分 | 说明 |
|---|---|---|
| 岗位契合度（业务执行型 / 平台型 Agent 岗） | ★★★★☆ | 与真实 JD 的模块要求高度重合（见 §2），是最大优势 |
| 差异化（相对简历池） | ★★★★★ | 市面应届项目大多是 chatbot/RAG/客服问答，流程执行型 + 可评测非常少见 |
| 与「Java+Python 结合」诉求的匹配 | ★☆☆☆☆ | PRD 现为**纯 Python**，且写"Java 功底体现在工程思维，不体现在此"——与你诉求冲突，需重构 |
| 面试追问纵深（可讲性） | ★★★★☆ | 状态机/幂等/HITL/审计/评测都有真问题可挖，前提是代码真的写完、指标真的跑出来 |
| 应届完成风险 | ★★☆☆☆ | 3 周 × 5h/天做完整套偏紧；"烂尾"是面试项目第一死因，必须预先定好砍单线 |

**一句话建议：保留"跨系统流程执行型 Agent"的定位（这是你最强的一张牌），做一次架构改造——流程引擎与 Mock 企业系统用 Java 写、Agent Harness 与评测用 Python 写（双服务、契约先行），并按 §4–§6 调整范围与叙事。**

## 2. 市场验证：这个 PRD 打中了什么、漏了什么

### 2.1 打中的（与真实 JD 逐条对应，这是项目最值钱的地方）

对照样本 A（智联 · Agent平台开发工程师，Java 栈）：

| PRD 设计点 | JD 原文要求 | 命中度 |
|---|---|---|
| 流程状态机（SQLite 持久化） | 智能体运行实例…**状态机控制**、异步执行、**失败恢复** | 完全命中 |
| HITL 审批（approve/reject/revise） | 任务取消、**审批中断** | 完全命中（PRD 甚至是超集） |
| 幂等 / 超时重试 / 补偿 | 失败恢复…幂等预占 | 完全命中 |
| 审计日志 + Trace 回放 | 链路追踪…**运行回放**及链路追踪能力 | 完全命中 |
| 模型路由（flash/pro）+ 成本护栏 | **模型路由**、预算预授权、token/cost 归因、降级 | 完全命中（PRD 是降维版） |
| 工具注册 + 参数校验 | 工具定义、**幂等预占、权限校验**、上下文快照、token 预算 | 完全命中 |
| Eval 端到端用例 + 指标 | 工作流编排、**观测评测** | 完全命中 |
| 流程主干声明式 + 可审计 | 架构方案拆解为可落地的接口设计、数据模型、服务边界、异常语义 | 叙事一致 |

样本 A 是 5-10 年社招 JD，却与你 2-3 周的 PRD 逐词对应——**说明这不是"玩具"，而是真实岗位核心模块清单的缩小版**。这是所有调研里最重要的发现。

样本 B（卓望 · 本科校招）说明业务向 Agent 岗要：工作流编排、多 Agent 协作、SKILL/MCP、Prompt、工具调用 + 扎实后端——PRD 主线已覆盖大半，缺口见 §2.2。

### 2.2 漏掉的 / 有风险的

1. **Java 完全不落地（最大问题）**。样本 B 写"Python 或 Java/Go 之一"，样本 A、F 是 Java 栈，阿里云 C 也列 Java。对以 Java 为主要后端的本科应届生：① 纯 Python 项目无法证明 Java 能力，Java 系岗位（国企/银行/服务商/大厂平台）直接失去抓手；② 与你的诉求"Java + Python 结合"冲突。**必须改**（方案见 §4）。
2. **JD 高频词没有进叙事**：MCP / SKILL / Function Calling / 工作流编排 / 多 Agent 协作 / 评测闭环。PRD 有对应实体（工具注册、路由、Eval）但**没用招聘语言命名**，简历/README 会被关键词筛掉。
3. **RAG / 向量库（加分项）完全没有**：样本 B/D/E 都把 RAG、向量库列为要求或加分。P2P 场景天然不需要 RAG——这本身是可以讲的取舍，但**必须在简历/README/面试里主动解释**，否则会被当成"不会 RAG"。可选项见 §5.2。
4. **应届生与"业务向"叙事之间有裂缝**：应届没有企业落地经验，PRD 强调"业务价值/岗位刚需"的写法容易在面试中被一句"这需求你哪来的 / 你在企业做过吗"问穿。**建议把定位从"企业业务价值"降为"以 P2P 为载体的 Agent 工程能力证明"，价值主张放到工程与评测上。**
5. **自研 Harness 的伴生风险**：JD 普遍要求"熟悉 LangChain/LangGraph/Dify"。只自研、不表态主流框架，会被误判为"不会用现成框架"。需要对照组（§5.2）与话术（§6.2）。
6. **完成度风险**：整套（Harness + 引擎 + 3 Mock + 面板 + Eval + 双语言化）按 3 周 × 5h 排太满。面试项目死于讲不出实测的烂尾，比死于范围小更常见。

## 3. PRD 本身的强项（保留，别动）

- **取舍叙事成熟**：workflow × agent 混合形态、主干声明式可审计、LLM 只管分支决策——对应 Anthropic 框架与 AgentGuide 的"框架选型 / 如何证明比人好"高频题，应届作品里少见。
- **可量化闭环**：Eval 集 + 自动化率 / token 成本 / 恢复率 / 审计完整率——正面回应"如何证明 Agent 有效"。
- **范围纪律**：Out-of-scope 表 + M12 永远可牺牲，说明作者理解蔓延风险。
- **异常旁路设计**（RETRYING / SUSPENDED / COMPENSATED）直接命中 JD 的"失败恢复 / 降级"关键词。
- **权限分级 + HITL** 命中样本 A 的"权限校验、审批中断"，也是花钱类 Agent 的安全卖点。

## 4. 必改 ①：Java + Python 双栈架构（推荐方案）

### 4.1 推荐：两个服务、一个契约

- **Python 服务（Agent 皮层）**：FastAPI 演示面板 / API；Agent Harness（ReAct loop）；工具注册（对齐 MCP schema）；意图解析 / 参数抽取 / 缺参澄清；模型路由 flash/pro + 成本护栏；Eval runner / Trace 回放。
- **Java 服务（流程骨架 / 企业侧）**：流程执行引擎（状态机 / 幂等 / 补偿 / 超时重试 / 审计 / 权限 / HITL 审批）；Mock 企业系统 ×3（oa / finance / scm）；SQLite（或 PG 抽象）。
- **通信**：HTTP + OpenAPI 契约先行；request_id / trace_id 从 Python 入口生成、全链路透传。

| 对比项 | Java 服务 | Python 服务 |
|---|---|---|
| 承担 | 流程执行引擎 + 3 个 Mock 企业系统 + HITL/审计 API | Agent Harness + LLM 调用 + 演示面板 + 评测 |
| 核心代码点 | 状态机（表驱动 / enum）、request_id 幂等、补偿（预算锁定失败→解锁）、append-only 审计、HITL suspend/resume、SQLite WAL 事务、错误码/契约 | ReAct loop、结构化输出 + Pydantic 校验 + 一次纠错重试、上下文分层与 token 预算、flash/pro 路由、Eval runner |
| 面试话术 | **确定性、资金安全、可审计的部分交给 Java 后端工程** | **不确定性、模型决策、实验迭代的部分交给 Python AI 生态** |
| 建议体量 | 真实工作量占比 50~60%（面试官会把 Java 当主语言） | 40~50% |

**为什么这个切法合理（面试也能讲）：** 样本 A/C 的 JD 把 Agent 运行时拆成"状态机 / 幂等 / 审计 / 调度"（确定性工程）与"模型网关 / 上下文 / 评测"（AI 工程）两类模块——你只是用两种语言各做一类，分工恰好与岗位 JD 的组织方式一致，还能顺势讲"跨语言服务如何用 request_id / trace_id 串起可观测性"。

### 4.2 双语言最容易翻车的点（提前规避）

1. **不要跨语言共享 SQLite**：Java 引擎持库（状态 / 审计）；Python 的 trace 落 JSONL 或独立小库；展示时按 trace_id 关联。共享同一文件库会陷入并发锁与方言差异的泥潭。
2. **契约先行**：Java 先出 OpenAPI 契约（POST /flows、POST /flows/{id}/approve、GET /flows/{id}/trace…），Python 按契约写 client。契约 + 错误码本身就是加分交付物。
3. **trace_id / request_id 全链路透传**：这是"可观测性"叙事的技术支点，Java/Python 两侧都要落日志。
4. 时间不够时的降级路径：**先让 Python 主干直连"Java Mock 系统"跑通**（Mock 是 Java 侧最轻的入口），引擎状态机再逐步从 Python 侧迁到 Java 服务；每一步都有可演示的东西。

### 4.3 备选方案（按意向岗位浓度选）

- **方案 B（若主要投 Java 系 AI 岗：国企 / 银行 / 服务商 / 平台）**：Java 做全部主干（Spring Boot + 自研状态机，不引 Activiti/Flowable 的理由照旧），Python 只做"LLM 胶水 + Eval 脚本"薄层。参考样本 F 的 Java 栈写法。
- **方案 C（若主要投 Python 系 AI 原生 / 创业公司岗）**：Python 主干不变，Java 只做 3 个 Mock 企业系统 + 一个流程引擎服务（约 600-1000 行，状态机 / 幂等 / 审计留在 Java）——Java 体量小但真实存在，能答"Java 写在哪"。
- **通用原则**：**主语言做到"深"，副语言做到"真"**。双语言浅尝辄止是减分项；一个语言一条线能讲穿、另一个语言有明确不可替代的职责，才是加分项。默认主推方案 A。

## 5. 必改 ②：范围、排期与完成度（对齐应届现实）

### 5.1 P0 / P1 / P2 重排（3 周 × 5h ≈ 75h，按方案 A 建议按 3.5~4 周排）

| 优先级 | 内容 | 验收（可演示即可，别追求完美） |
|---|---|---|
| **P0 最小可讲闭环**（先做，约 50h） | Java Mock ×3 + 简单流程引擎 + Python ReAct Harness（工具注册 / 结构化输出 / 一次澄清）+ 一条主链路（一句话→抽取→审批→下单→付款）+ HITL 一个节点 + SQLite 审计 + CLI / 最简页面演示 | 录屏 3 分钟：一句话发起→全程状态推进→审批→完成→审计回放 |
| P1 工程完备 | 幂等 / 补偿 / 超时重试（故障注入演示）、权限分级、驳回修订重提、Eval 15 条跑分、trace 落库回放 | README 写清：通过率 / 自动化率 / 成本对比三张图 |
| P2 加分（有时间才做） | supervisor 多 Agent（对齐"多 Agent 协作"关键词）、一个工具用 MCP 协议暴露、Docker 一键起、LangGraph 对照 demo | 简历可写"加分项"；没做不写 |

### 5.2 与 JD 关键词对齐的最小动作（几乎不花时间，收益大）

- 命名层：README 与简历直接使用 JD 词——**工作流编排、状态机 / 失败恢复、审批中断(HITL)、工具调用幂等、模型路由与成本护栏、评测闭环、审计 / 可观测**。PRD 里的东西换皮即可。
- 工具注册层做"类 MCP schema"时，直接兼容一段 MCP 工具的 JSON Schema 格式，并在文档写一句"与 MCP 工具协议对齐，可平滑接入 MCP Server"。
- 加一张"**为什么本项目不需要 RAG**"FAQ：P2P 是动作执行场景，决策所需信息在结构化单据里，不需要向量检索非结构化知识；如面试官追问，给一个把"供应商知识库查询"作为可选工具的扩展点即可。**不要为关键词硬加 RAG。**

### 5.3 应届身份下的叙事修正

- 把"企业侧第一大刚需"这类 PRD 口吻换成工程口吻：**用 P2P 业务作载体，自证 Agent 系统工程能力——确定性流程（Java 引擎）与模型决策（Python Harness）如何分工、如何让它可审计、可恢复、可评测**。
- 所有指标等 M8/M10 实测出来再写；没跑的数字一个都不写（PRD 已遵守，保持）。

## 6. 必改 ③：简历、README 与面试防御

### 6.1 简历三条（示例，做完 P0+P1 后填数）

> **跨系统采购到付款（P2P）流程执行型 Agent（Java + Python 双服务）**
> 1. 架构：Java 实现流程执行引擎（状态机 / SQLite 持久化 / request_id 幂等 / 补偿 / append-only 审计 / HITL 审批中断与恢复）+ 3 个可故障注入的 Mock 企业系统；Python 实现自研 Agent Harness（ReAct loop、类 MCP 工具注册、结构化输出校验、flash/pro 模型路由与 token 成本护栏）；双服务 HTTP 契约 + trace_id 全链路贯穿。
> 2. 业务：自然语言发起采购 → 引擎跨 OA/财务/采购完成预算校验、审批、下单、验收、付款；支持澄清、驳回修订、预算不足建议；高风险动作人工确认。
> 3. 结果：15+ 端到端用例通过率 X%、无需人工干预率 X%、模型路由使单流程 token 成本下降 X%、故障注入后自动恢复率 X%、审计可回放率 100%（实测后填数）。

### 6.2 高频追问防御清单（对照样本 G 自查）

- 状态机为什么不用 Activiti/Flowable / 为什么不引 LangGraph？→ 主干要可审计可回滚可测试，花钱动作不交给 LLM 自由编排；对比过 Flowable 重引擎与 LangGraph 的 checkpointer 思路后自研轻量版（能讲清 LangGraph 的 StateGraph / 节点边 / 持久化是什么）。
- 工作流引擎设计题（样本 G 原题）→ 你的状态机 + 分支 / 循环 / 重试 / 持久化就是答案素材。
- 如何证明 Agent 比人好 / 比上一个方案好？→ 用 Eval 集 + 自动化率 + 成本数字回答（PRD §7 指标正好用上）。
- 重试 / 幂等怎么做？→ 指数退避 + 上限 + request_id 唯一约束 + 重复请求返回原结果（PRD §5 有，代码里要真的实现）。
- 审批中断后进程重启怎么办？→ SQLite 持久化 + 恢复扫描挂起单（P0 就要有的能力，别只写文档）。
- HITL 人机边界怎么定？→ 权限分级：只读 / 低风险执行 / 花钱必须人工确认；金额阈值规则化。
- 为什么不用现成框架 / 你了解 LangChain 吗？→ 讲清取舍 + 做过对照实验（哪怕只跑通一个 LangGraph demo）。
- RAG 你们没有？→ 用 §5.2 的 FAQ 话术。
- 多 Agent 呢？→ supervisor 是 P2 加分项；没有则讲"当前单 Agent + 确定性引擎已覆盖，多 Agent 在流程执行场景引入的上下文 / 成本开销不划算"。

### 6.3 交付物三件套

1. **README.md**：架构图 + 一分钟 demo 录屏 + 三个实测指标 + 取舍说明 + FAQ。
2. **评测报告**：15-20 条用例表 + 通过 / 失败 / 失败原因分析（"失败分析"是亮点，PRD 已列）。
3. **架构图 + 追问清单**：一页能讲 5 分钟的故事线（从"一句话"讲到"审计回放"）。

## 7. 结论与下一步

1. **方向值得做**：业务执行型 / 流程型 Agent 是目前校招本科可够到的岗位里，与 PRD 能力点重合度最高的方向；智联 / 卓望 / 阿里云的 JD 直接验证"状态机、幂等、HITL、评测、路由、审计"正是岗位要的模块。
2. **三个必改**：① Java 真实上阵（§4 方案 A，双服务契约先行）；② 范围压到 P0 优先、先出 3 分钟录屏闭环再谈完备性（§5）；③ 叙事与关键词对齐 + 应届身份化修正（§5.3、§6）。
3. **下一步建议**：(a) 按 §4 的架构更新 PRD 的技术栈与里程碑为双语言版本；(b) 先花 1-2 天做"Java Mock 系统 + 契约 + 连通性"冒烟，验证双语言链路不卡壳；(c) 之后严格按 P0 → P1 推进，每周产出一个可录屏的增量。
